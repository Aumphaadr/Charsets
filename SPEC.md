# Charsets — спецификация

Учебный сайт о кодировках символов. Отвечает на вопрос
«почему человечество не придумало одну кодировку на все случаи жизни».

Статус: черновик, обсуждается до написания кода.

---

## 1. Понятийная модель

Ключ ко всему сайту — развести три слоя, которые в быту называют одним
словом «кодировка». Смешение этих слоёв и есть источник вопроса студента.

| Слой | Что отображает | Представители |
|---|---|---|
| **Кодовая страница** (charset / code page) | байт 0..255 → символ | ASCII, Windows-1251, Windows-1252, CP866, KOI8-R, CP850, ISO-8859-1 |
| **Форма кодирования Unicode** (encoding form) | кодовая точка U+0000..U+10FFFF → последовательность байтов | UTF-8, UTF-16 |
| **Транспортное кодирование** (binary-to-text) | произвольные байты → печатный текст | Base64 |

Следствия для интерфейса:

* Base64 **не** равноправен CP866 в одном списке. У него нет отношения
  «код → символ» в том же смысле; у него алфавит из 64 символов.
  В комбобоксе — отдельная группа за визуальным разделителем,
  таблица своя (индекс 0..63).
* Для однобайтовых кодировок «номер строки» = байт = единственное число.
* Для UTF-8/UTF-16 «номер строки» = кодовая точка, а колонки DEC/HEX/BIN
  показывают **последовательность байтов** переменной длины.
  Контраст в одной таблице объясняет UTF-8 нагляднее любого текста:

  ```
  U+0041  A   41                 (1 байт)
  U+0416  Ж   D0 96              (2 байта)
  U+4E2D  中   E4 B8 AD           (3 байта)
  U+1F600 😀  F0 9F 98 80        (4 байта)
  ```

## 2. Что умеет платформа (проверено на V8/ICU)

### Байты → текст: нативно

`TextDecoder` реализует WHATWG Encoding Standard. Подтверждённо работают:
`utf-8`, `utf-16le`, `utf-16be`, `windows-1251`, `windows-1252`,
`ibm866` (алиас `cp866`), `koi8-r`, `koi8-u`, `iso-8859-5`, `macintosh`,
`x-mac-cyrillic`, `big5`, `shift_jis`, `euc-kr`, `gbk`.

Таблица кодовой страницы строится одним прогоном, без данных в репозитории:

```js
const dec = new TextDecoder('windows-1251');
const table = Array.from({length: 256}, (_, b) => dec.decode(new Uint8Array([b])));
```

Декодировать надо **побайтно**, а не одним массивом: иначе многобайтовые
кодировки склеят соседей.

### Текст → байты: нативно только UTF-8

`new TextEncoder('windows-1251')` молча игнорирует аргумент —
`.encoding` всегда `'utf-8'`. Обратное отображение получаем инверсией:

```js
const rev = new Map(table.map((ch, i) => [ch, i]));   // rev.get('Ю') === 222
```

Символ, которого нет в `rev`, — непредставим в этой кодировке.
Это не ошибка реализации, а **главная демонстрация сайта**.

### Три места, где платформе верить нельзя

| Запрос | Что реально отдаёт | Почему это проблема |
|---|---|---|
| `TextDecoder('ascii')` | `windows-1252` | Байт 0xE9 отдаст `é`. Для сайта про ASCII — ложь. |
| `TextDecoder('iso-8859-1')` | `windows-1252` | Настоящий Latin-1 держит в 0x80–0x9F управляющие C1, а не типографику Microsoft. |
| `TextDecoder('cp850')` | **исключение** | Не поддержан ни как `cp850`, ни как `ibm850`. |

Значит, нужны три собственные таблицы: ASCII, ISO-8859-1, CP850.
Формат — строка из 128 символов (только верхняя половина, 0x80..0xFF);
для ASCII верхняя половина пуста, все 128 слотов неназначены.
Цена: ~256 байт на кодировку.

Расхождение `iso-8859-1` / `windows-1252` стоит вынести на сайт отдельным
сюжетом: это готовый ответ на вопрос «а почему не договорились».

### Base64

`btoa`/`atob` работают только с latin1 — `btoa('Привет')` бросает
`InvalidCharacterError`. Классические грабли; показываем их явно,
а правильный путь строим через `TextEncoder` → байты → алфавит Base64.

## 3. Единый интерфейс кодировки

Всё разнообразие прячется за одним объектом, страница о нём не знает:

```js
{
  id:    'windows-1251',
  title: 'Windows-1251',
  kind:  'sbcs' | 'unicode' | 'transport',
  range: [0, 255],              // либо [0, 0x10FFFF]
  bytesPerRow: 1 | 'variable',

  // код → строка таблицы
  row(code) => {
    char:   string | null,      // отображаемый глиф
    bytes:  Uint8Array,         // для DEC/HEX/BIN
    status: 'ok' | 'control' | 'unassigned' | 'surrogate' | 'noncharacter',
    label?: string              // 'NUL', 'DEL' — мнемоника для управляющих
  }
}
```

Реализации: `SbcsCharset` (из TextDecoder или из своей таблицы),
`Utf8Charset`, `Utf16Charset` (LE/BE + вопрос BOM), `Base64Alphabet`.

## 4. Страница «Обозреватель кодировок»

### Шапка

```
[≡]  [ Кодировки: Windows-1251 +2 ▾ ]        [x]CHAR [x]DEC [ ]HEX [ ]BIN
```

* Бургер слева → выезжающее боковое меню (пункты прорабатываются отдельно).
* Мультиселект по центру (см. раздел 5) с поиском и двухуровневой
  группировкой — кодировок под сорок, плоским списком не обойтись:
  * *Кодовые страницы* → DOS (CP437, 850, 852, 855, 857, 866),
    Windows (1250…1258), ISO 8859 и ASCII (ASCII, 8859-1…16),
    КОИ-8 и Macintosh (KOI8-R, KOI8-U, Mac Roman, Mac Cyrillic)
  * *Формы Unicode*: UTF-8, UTF-16 LE/BE, UTF-32 LE/BE
  * *Транспортные*: Base64
* Переключатель записи кода `Код: [раздельно] [слитно]`. Два взгляда на
  одно и то же, и обоим есть законное применение:

  | Строка | раздельно | слитно |
  |---|---|---|
  | 256 | `1 0` · `01 00` · `00000001 00000000` | `256` · `0100` · `0000000100000000` |
  | 3341 | `13 13` · `0D 0D` | `3341` · `0D0D` |

  «Раздельно» показывает, что байтов два; «слитно» — значение
  последовательности. Выбирать за пользователя тут нечего.

  Действует и в режиме «по символу», причём там всплывает приятный
  побочный эффект: слитный UTF-32 для `А` даёт `1040` — ровно номер
  кодовой точки, а UTF-16 LE даёт `4100`, и сразу видно, что порядок
  байтов переставлен.

  Переключение перерисовывает ленту (меняется сама разметка строк),
  позиция прокрутки сохраняется. Ширины пересчитываются: слитная запись
  короче, разделителей нет, а десятичная длина считается по наибольшему
  значению — два байта это 65535, пять знаков, а не шесть.

* Регулятор кегля таблицы `[−] 22 [+]` в духе MDEditor, диапазон 10…24.
  По умолчанию крупный: типовой сценарий — показать таблицу, а не уместить
  побольше столбцов. Кому нужно много кодировок рядом, уменьшит вручную.
  Меняет только переменную `--fs` и ширины колонок — разметка не
  перерисовывается, содержимое строк от кегля не зависит.
* Чекбоксы справа: `CHAR` неотключаем (`disabled`, но визуально активен),
  `DEC` активен по умолчанию, `HEX` и `BIN` выключены.
  У каждого — подсказка при наведении (свой тултип, не `title=`:
  нативный медленный и не стилизуется).

### Основной блок

Таблицы по 32 строки. Границ три уровня, и они должны читаться именно
в этом порядке:

| Граница | Как выглядит |
|---|---|
| между строками | тонкая линия, `--c-border` |
| середина таблицы, 16/16 | 2 px, `--c-border-strong` |
| стык таблиц, каждые 32 строки | 2 px плюс просвет 9 px |

Разделитель 16/16 делает видимой структуру: половина таблицы = 16 кодов =
одна колонка классической шестнадцатеричной раскладки.

Первая реализация про третий уровень забыла: последняя строка таблицы
получала обычную тонкую линию, и стык 31/32 был неотличим от любой другой
строки. Получалась перевёрнутая иерархия — внутренний разделитель выглядел
крупнее внешнего, хотя внешний структурно главнее.

### Полосы прокрутки

Системная полоса на тёмном фоне — единственное светлое пятно на странице,
и в обозревателе она особенно на виду: длинная и постоянная.

Держим два набора правил сразу. Стандартные `scrollbar-color` понимают
Chrome от 121, Firefox и свежий Safari; `::-webkit-scrollbar` остаётся
для старого Safari. Там, где работают стандартные, псевдоэлементы браузер
игнорирует сам — замер это подтвердил: заданные 12 px ширины не применились,
осталась платформенная 15 px. Значит форму и стрелки полосы мы не
контролируем, только цвет — и это разумная цена за то, что цвет верен
во всех браузерах, а не в одном.

Дорожка совпадает с фоном той поверхности, на которой лежит: в ленте это
`--c-bg`, в боковом меню и в списке кодировок — `--c-surface`.

### Таблица по центру

Таблица уже экрана почти всегда, а прижатая к левому краю выглядит
брошенной. Центрируется каждая таблица (`margin: 0 auto`) — ширины у всех
одинаковые, поэтому липкая шапка и тело центрируются согласованно.
Когда таблица шире экрана, `margin: auto` обращается в ноль и включается
горизонтальная прокрутка контейнера.

### Никаких разрывов

Таблица показывает **каждую** позицию диапазона подряд, без пропусков.
Если с 0x00 по 0xE1 идут внятные символы, дальше до 0xFF ничего нет,
а с 0x100 снова начинается содержательное — незанятые позиции всё равно
занимают свои строки и показывают отсутствие символа явно.

Причина педагогическая: «в этой кодировке здесь пусто» — такой же факт
о кодировке, как и наличие буквы. Свёрнутый диапазон превращает факт
в невидимость, и студент решает, что там что-то есть, просто не показали.

### Объём и навигация

Замерено в Chrome (headless, без GPU — оценка пессимистичная).
Строка = 4 ячейки, таблицы по 32 строки.

Наивная реализация деградирует быстро, причём узкое место — не вставка
строк, а **переключение колонки**: смена `display` на тысячах ячеек
вызывает пересчёт раскладки всего документа.

| Строк | Отрисовка | Переключение колонки |
|---|---|---|
| 4 096 | 343 мс | 89 мс |
| 16 384 | 1 495 мс | 345 мс |
| 65 536 | 3 132 мс | 1 449 мс |

Два изменения в CSS убирают проблему целиком:

```css
.block { content-visibility: auto; contain-intrinsic-size: auto 1120px; }
table  { table-layout: fixed; }
```

`content-visibility: auto` разрешает браузеру пропускать раскладку блоков
за пределами экрана; `table-layout: fixed` избавляет от измерения
содержимого ячеек. Те же замеры после правки:

| Строк | Отрисовка | Переключение колонки |
|---|---|---|
| 4 096 | 23 мс | 0.1 мс |
| 16 384 | 66 мс | 0.1 мс |
| 65 536 | **143 мс** | **0.2 мс** |
| 131 072 | 299 мс | 0.4 мс |

Вывод: **весь BMP грузится целиком за ~150 мс.** Пагинация не нужна,
виртуальный скролл не нужен, «Показать ещё» работает свободно.

### Принятая модель: непрерывная лента с догрузкой

* Таблица начинается с кода 0 и растёт вниз. Ничего не выгружается.
* Порция догрузки — **банк** из 256 кодов = ровно 8 таблиц по 32 строки.
  Размер выбран так, чтобы совпадать с ментальной моделью «одна кодовая
  страница».
* Под лентой: `Показать ещё 256` · `Показать ещё 4096` · `Показать всё`.
  Последняя кнопка честно доступна — замеры позволяют.
* В режиме 1 банк один, кнопок догрузки нет. Но и молчать нельзя:
  пользователь, выбравший в том числе формы Unicode, ждёт продолжения.
  Поэтому конец ленты объясняет причину и предлагает выход:

  > Ось байта закончилась: одним байтом больше 256 значений не выразить.
  > **[Смотреть дальше — по символу]**

  Кнопка переключает в режим 2 прямо оттуда. Формулировка про ось, а не
  про «кодовую страницу»: в наборе могут быть UTF-8 и UTF-32, которые
  кодовыми страницами не являются.

### Плоскости выше BMP

U+10FFFF — это 1 114 112 кодов, 5.6 млн узлов DOM. Одной лентой не влезет.
Решение, сохраняющее непрерывность: **BMP — основная лента**, плоскости
1–16 (SMP и далее) выбираются отдельно и каждая является своей
непрерывной лентой на 65536 кодов. Переход между плоскостями подписан
(«Плоскость 1, дополнительная многоязычная, начинается с U+10000»),
то есть это не скрытый разрыв, а явная смена области.

### Длительные действия — порциями, с индикатором

Замеры на прототипе разделили действия на два класса.

**Дешёвые — те, что можно свести к одному атрибуту на контейнере.**
Переключение DEC/HEX/BIN стоит 23 мс даже на полном BMP. Приглушение
совпадающих строк сначала было сделано перерисовкой и вешало страницу на
секунды; исправлено тем, что признак «сравнивать нечего» проставляется
на строку при отрисовке (`data-same`), а галочка гасит их чистым CSS —
20 мс вместо секунд. Правило общее: если признак зависит от набора
кодировок, но не от самой галочки, его место в разметке, а не в
обработчике.

**Дорогие — те, где перерисовка неизбежна**: смена набора кодировок,
смена режима, догрузка банков. Здесь лента собирается порциями:

* банки добавляются по одному, управление возвращается браузеру, как
  только на текущий кадр набралось 12 мс работы;
* пока идёт сборка, под шапкой видна полоса хода, а список кодировок,
  переключатель режимов и кнопки догрузки заблокированы — иначе
  пользователь успевает натыкать новых заданий поверх недоделанного;
* счётчик поколений: отрисовка, которую обогнала более свежая, бросает
  себя сама.

Полоса живёт под шапкой, а не внизу ленты: внизу она оказывается за
экраном ровно тогда, когда нужна.

### Показать меньше

Обратная кнопка обязательна. Набрав 65 536 строк, пользователь оказывается
в ленте, где любая перерисовка стоит секунду с лишним, и выхода из этого
состояния без перезагрузки быть не должно. «Показать меньше» сворачивает
ленту до первых 256 строк удалением лишних блоков из DOM — 39 мс.

### Переключение колонок — только CSS

Ячейки HEX и BIN рендерятся всегда и скрыты стилем:

```css
.c-hex, .c-bin { display: none; }
[data-cols~="hex"] .c-hex { display: table-cell; }
[data-cols~="bin"] .c-bin { display: table-cell; }
```

Чекбокс меняет один атрибут на контейнере. С `content-visibility` это
0.2 мс на полном BMP.

Формат BIN: группировка по байтам через пробел (`11010000 10010110`).
Для однобайтовых — ровно 8 бит, ширина колонки фиксирована.

### Тексты подсказок

Параллельная формулировка: четыре колонки — четыре представления одного
и того же, и подписи это подчёркивают.

* **CHAR** — «Символьное представление»
* **DEC** — «Десятичное представление»
* **HEX** — «Шестнадцатеричное представление»
* **BIN** — «Двоичное представление»

## 5. Режим сравнения — несколько кодировок сразу

Комбобокс заменён на **выпадающий список с чекбоксами**: можно смотреть
две-три кодировки бок о бок и видеть, во что превращается один и тот же
код в каждой из них. На FullHD место для этого есть с запасом (замеры ниже).

### Два режима сравнения

Переключатель на два положения, подписанный словами владельца:

**Режим 1 — «один код, разные символы».**
Слева ось: последовательность байтов. Справа по группе колонок на кодировку,
в них символы. Строка `11000000` (192, `C0`):

| Windows-1251 | Windows-1252 | CP866 | KOI8-R |
|---|---|---|---|
| `А` | `À` | `└` | `ю` |

Ось не останавливается на 255: дальше идут двухбайтовые последовательности,
и вот там режим показывает свой главный экспонат. Строка 53 392 — это
байты `D0 90`:

| UTF-8 | Windows-1251 | CP866 | KOI8-R |
|---|---|---|---|
| `А` | `Рђ` | `╨Р` | `п▒` |

Прокрутка по этому участку читается так: в столбце UTF-8 идёт русский
алфавит подряд — А, Б, В, Г, Д, — а в соседних столбцах в тех же строках
абракадабра. Это буквально механизм кракозябр, разобранный по байтам,
а не рассказанный на пальцах.

Верхняя граница режима — 65 535, то есть одно- и двухбайтовые
последовательности. Дальше лента не идёт не из-за недогруза, а из-за
размера пространства: трёхбайтовых 16 777 216, четырёхбайтовых
4 294 967 296. Так и написано в конце ленты — сам по себе неплохой довод
в пользу того, почему кодировки устроены сложно.

**Режим 2 — «один символ, разные коды».**
Слева ось: символ. Справа по группе колонок на кодировку, в них числа.
Строка `А` (U+0410):

| Windows-1251 | Windows-1252 | CP866 | KOI8-R | UTF-8 |
|---|---|---|---|---|
| `C0` | непредставим | `80` | `E1` | `D0 90` |

Отвечает на «почему мой текст не сохраняется в этот формат».

Режимы цепляются друг за друга: буква `А` и байт `C0` встречаются в обоих
примерах, но в разных ролях. Это удобно как пара слайдов.

**Кнопка «смотреть дальше» убрана.** В первом прототипе конец ленты
режима 1 предлагал перейти в режим 2 — то есть переключал режим за
пользователя, нарушая его же правило «строго вручную». После продолжения
оси двухбайтовыми последовательностями надобность отпала: лента просто
едет дальше.

**Автовыбор режима отвергнут.** Была идея угадывать режим по набору галочек.
Отказались: режим — осознанное намерение пользователя, а автоматика, молча
меняющая смысл левой колонки, на учебном сайте опаснее лишнего клика.

Решение оказалось не только педагогическим, но и архитектурным: без
автоматики ось **жёстко** привязана к режиму, и вся условная логика
диапазонов исчезает.

* Режим 1 — ось всегда байт, ровно 256 строк. Это классическая таблица
  кодовой страницы.
* Режим 2 — ось всегда кодовая точка, лента до U+10FFFF с плоскостями.

Исходная постановка задачи («0..255 для восьмибитных, 0..65535 для
остальных») — это ровно два этих режима, а не одна страница с ветвлением.
Лента с догрузкой и `content-visibility` нужны, соответственно, только
в режиме 2.

**Подписи переключателя** (лаконичные, полная формулировка — в подсказке):

```
Сравнивать:  [ по коду ]  [ по символу ]
             ↑ «Один код — разные символы»
                          ↑ «Один символ — разные коды»
```

### Что меняется между режимами

| | Режим 1 | Режим 2 |
|---|---|---|
| левая ось | число (байт / кодовая точка) | символ + имя Unicode |
| в группе кодировки | `CHAR` + DEC/HEX/BIN | DEC/HEX/BIN + «представим?» |
| чекбоксы в шапке | CHAR (неотключаем), DEC, HEX, BIN | DEC, HEX, BIN |
| диапазон | 0..65 535 (одно- и двухбайтовые) | весь Unicode |

`CHAR` в режиме 2 не исчезает как понятие — он становится осью, поэтому
и уходит из набора чекбоксов.

В режиме 2 с одними кодовыми страницами почти весь диапазон выше 255 —
«непредставим». Строки всё равно показываются (принцип «не рвать»),
но гасятся тем же приглушением, что и совпадающие.

### Служебные состояния — значками, не словами

Первый прототип писал в ячейку слова: «продолжающий байт», «половина
единицы», «непредставим». Это съедало ширину столбца и превращало таблицу
в текст. Заменено значками с подсказкой при наведении.

**Управляющие символы** — мнемоника в рамке: `NUL`, `LF`, `CR`, `DEL`, `SP`.
Это ровно то, чем являются глифы Unicode-блока Control Pictures
(U+2400…U+243F), но брать их оттуда нельзя: блока нет ни в DejaVu Sans Mono,
ни в Noto Sans Mono — вышли бы квадраты. Поэтому рамка рисуется CSS-ом:
зависимости от шрифта ноль, ширина как у одного символа, кегль следует
за общим регулятором. Подсказка даёт расшифровку: «LF — перевод строки
(U+000A)».

**Остальные состояния** — знаки, наличие которых в шрифте проверено:

| Значок | Что означает |
|---|---|
| `·` | в этой кодировке позиция не занята |
| `…` | продолжающий байт UTF-8: сам по себе символа не даёт |
| `2` `3` `4` | начало последовательности такой длины |
| `⊘` | так не бывает: недопустимый байт, недопустимая последовательность, непредставимый символ |
| `½` | половина кодовой единицы UTF-16 |
| `¼` | четверть кодовой единицы UTF-32 |
| `◌` | суррогатная половина, не самостоятельный символ |

`½` и `¼` подобраны не для красоты: они и означают ровно то, что показывают.

Подсказки — свои, не нативный `title`: он медленный, не стилизуется и
обрезает длинный текст. Реализация — один плавающий элемент на страницу
и делегирование событий; вешать обработчик на каждую ячейку при 65 536
строках нельзя.

### UTF-8 в режиме 1

Побочный эффект режима 1 — готовая иллюстрация устройства UTF-8.
Каждый байт получает свой статус:

| Байты | Что показываем |
|---|---|
| `00`–`7F` | сам символ — совпадение с ASCII видно глазами |
| `80`–`BF` | продолжающий байт, самостоятельного значения нет |
| `C2`–`DF` | начало двухбайтовой последовательности |
| `E0`–`EF` | начало трёхбайтовой |
| `F0`–`F4` | начало четырёхбайтовой |
| `C0`, `C1`, `F5`–`FF` | не встречается никогда |

Одна таблица вместо получаса у доски.

### Виджет выбора

Нативный `<select multiple>` не годится: не стилизуется, не группируется
по-человечески, на сенсорных экранах ведёт себя непредсказуемо. Свой:

* Кнопка в шапке показывает состояние: `Windows-1251 +2`.
* Панель — те же три группы, что в разделе 1, с заголовками.
* **Порядок колонок = порядок в списке**, а не порядок выбора: столбцы
  не должны прыгать при снятии галочки.
* Порядок меняется **перетаскиванием** заголовков — принято владельцем.
  Реализация: тащим «фишки» верхнего уровня липкой шапки, живой предпросмотр
  идёт только по шапке (дёшево), тело перестраивается один раз на отпускании.
  Полная перерисовка BMP стоит ~150 мс, а перетаскивание — действие редкое,
  в отличие от чекбоксов. Порядок попадает в хеш URL.
* Минимум одна кодировка всегда выбрана — снятие последней запрещено,
  по той же логике, что и неотключаемый `CHAR`.
* `role="listbox"`, `aria-multiselectable="true"`, стрелки / Space / Esc.
* Внизу панели — счётчик и «Оставить одну».

### Шапка таблицы

Двухуровневая и липкая (`position: sticky`) — при 65536 строках без этого
через два экрана уже не помнишь, где чей столбец.

* верхний уровень: имя кодировки, `colspan` по её колонкам;
* нижний: CHAR / DEC / HEX / BIN;
* между группами кодировок — вертикальная граница `--c-border-strong`,
  чтобы глаз не смешивал соседние.

### Подсветка расхождений (опция, по умолчанию выключена)

Флажок «приглушить совпадающие строки» гасит до `--c-text-dim` те строки,
где сравнивать нечего. Что считается «нечего» — своё в каждом режиме:

* **режим 1** — все выбранные кодировки дают один и тот же символ
  (Windows-1251 и Windows-1252 совпадают на всём диапазоне 0..127);
* **режим 2** — либо символ непредставим везде, либо все кодировки
  записали его одними и теми же байтами (так выглядит весь ASCII
  практически в любом наборе).

Именно приглушить, а не свернуть: принцип «не рвать» из раздела 4
действует и здесь.

### Ловушка, найденная на прототипе: скрытая ячейка ломает выравнивание

Первая реализация прятала колонку через `display: none` на ячейке. Это
неверно: ячейка при этом **исчезает из строки**, и все следующие съезжают
в освободившиеся слоты колонок. Тело таблицы разошлось с шапкой ровно на
один столбец — под заголовком «Windows-1252» показывались данные CP866.

Правильно — оставить ячейку на месте и схлопнуть её в нулевую ширину
вместе с её `<col>`:

```css
.c-dec, .c-hex, .c-bin { padding: 0; font-size: 0; overflow: hidden; }
[data-cols~="hex"] .c-hex { padding: 3px 10px; font-size: 14px; }
col.w-hex { width: var(--w-hex-eff); }
```

Свойство «переключение колонок стоит доли миллисекунды» при этом
сохраняется: меняется по-прежнему один атрибут на контейнере.

### Шапка: два уровня, две роли

Уровни шапки живут по разным правилам, и оба раза первая реализация
ошиблась в одну сторону — служебная подпись оказывалась крупнее главной.

* **Имя кодировки** набрано **ровно текущим кеглем**. Это не украшение:
  из того же кегля считается ширина столбца, и любое расхождение сразу
  даёт обрезку. В первой версии имя было прибито к 11 px и не росло
  вместе с кеглем вообще.
* **Подписи колонок** (`CHAR`, `DEC`, `HEX`, `BIN`) растут вместе с кеглем,
  но упираются в потолок 13 px: при кегле 22 они начинали спорить с именем
  кодировки, а при 10 должны оставаться читаемыми.

### Ширину столбца задаёт заголовок, а не данные

При `table-layout: fixed` и автоматической ширине Chrome растягивает
таблицу по содержимому первой строки. Раз имя кодировки длиннее любого
глифа, ширину группы задаёт именно оно; общая ширина таблицы считается
из тех же переменных:

```css
.viewport table { width: calc(var(--w-axis) + var(--n-sets) * var(--w-group)); }
```

Без этого восемь соседних таблиц банка расходятся между собой и с шапкой.

К вычисленной ширине добавляются 4 px запаса. Причина мелкая, но
показательная: у заголовка группы есть левая граница в 1 px, и при
`border-collapse` она съедает пиксель из ширины столбца — «Windows-1251»
обрезалось многоточием ровно на один пиксель. Ширина знака тут ни при чём:
у DejaVu Sans Mono она измерена как 0.6021 em и одинакова для обычного
и полужирного начертания.

### Ширины (замерено в Chrome, DejaVu Sans Mono 14px, padding 10px)

Колонка кода — 72 px, дальше на каждую кодировку:

| Набор колонок | Однобайтовая | Влезает на 1920 | на 1366 |
|---|---|---|---|
| CHAR + DEC | 77 px | 23 | 16 |
| CHAR + DEC + HEX | 115 px | 15 | 10 |
| CHAR + DEC + HEX + BIN | 204 px | 8 | 6 |

| Набор колонок | UTF-8 (до 4 байт) | Влезает на 1920 | на 1366 |
|---|---|---|---|
| CHAR + DEC | 178 px | 10 | 6 |
| CHAR + DEC + HEX | 292 px | 6 | 4 |
| CHAR + DEC + HEX + BIN | 609 px | 2 | 2 |

Узкое место одно: UTF-8 с включённым BIN — `11110000 10011111 10011000
10000000` занимает 317 px. При переполнении горизонтально прокручивается
**контейнер таблицы**, а не `body`: липкая шапка и боковое меню остаются
на месте.

## 6. Страница «Перекодировщик»

Стенд, где механизм из таблицы можно потрогать руками. Конвейер:

```
Текст ──[записать как X]──▶ байты ──[прочитать как Y]──▶ текст
```

Если X и Y разные, на выходе кракозябры — и видно, из чего именно они
складываются. Классические пары вынесены в кнопки:

| Пара | «Привет, мир!» превращается в |
|---|---|
| UTF-8 → Windows-1251 | `РџСЂРёРІРµС‚, РјРёСЂ!` |
| Windows-1251 → Windows-1252 | `Ïðèâåò, ìèð!` |

Первая — самая частая в жизни: так выглядит UTF-8, прочитанный «по-старому».

### Два разворота, оба в секции «Байты»

Разворот — действие над направлением потока, а не над кодировкой чтения,
поэтому кнопки живут в середине конвейера, а не рядом со вторым списком.

**«⇅ Поменять кодировки»** — меняет местами только кодировки, текст
остаётся прежним. На большинстве данных выходит сплошная стена
недопустимых последовательностей: `Привет, мир!` через 1251 → UTF-8 даёт
`⊘⊘⊘⊘⊘⊘, ⊘⊘⊘!`. Это законный вопрос «а что если прочитать наоборот»,
и подсказка на кнопке честно предупреждает о результате.

**«↺ Прогнать обратно»** — результат становится исходным текстом,
и кодировки меняются местами. Это точная обратная операция:

```
Привет, мир!  →UTF-8→  байты  →1251→  РџСЂРёРІРµС‚, РјРёСЂ!
РџСЂРёРІРµС‚, РјРёСЂ!  →1251→  байты  →UTF-8→  Привет, мир!
```

Байты на обоих проходах совпадают побайтно. Это не удобство, а отдельный
инструмент: именно с этой задачей — «мне прислали кракозябры, верните
текст» — человек и приходит. Работает и после ручной правки байтов.

Кнопка инволютивна: нажатие дважды возвращает в исходное состояние —
то есть снова портит текст. Это последовательно (кнопка разворачивает
любое направление, включая собственный результат), но означает, что
подпись под результатом не вправе объявлять разворот успехом.

### Подпись под результатом — только о том, что видно

Здесь дважды наступили на одни грабли, и второй раз показателен.

**Первая ошибка.** Подпись писала «отсюда и кракозябры» всякий раз, когда
кодировки различались. Но любой латинский текст через 1251 → 1252 проходит
без единого изменения — заявлять о кракозябрах над неизменившимся текстом
было ложью.

**Вторая ошибка, ровно того же рода.** Добавили ветку «развернули обратно»,
которая срабатывала по нажатой кнопке. Ловится в два нажатия: «Прогнать
обратно» с уже целого текста снова его портит, а подпись продолжала
рапортовать об успехе — рапорт поверх кракозябр.

Вывод, стоивший двух заходов: **подпись не должна судить по действию,
только по наблюдаемому состоянию.** Направление процесса страница не знает
и знать не может — ломают текст и лечат его одним и тем же действием,
и по результату они неразличимы.

| Что видно | Что пишем |
|---|---|
| кодировки совпадают | текст возвращается без потерь |
| кодировки разные, результат совпал с исходником | текст целиком в их общей части |
| кодировки разные, результат отличается | правила разные, поэтому текст другой; так кракозябры и появляются, и той же кнопкой разворачиваются обратно |

Последняя формулировка верна в обе стороны и никогда не спорит с тем,
что видно на экране.

Для сравнения результата с исходником потребовался `decodeText()` в модели:
он отдаёт настоящую строку, а не части со значками.

### Ширина конвейера тянется за кромки

Наведение на левую или правую кромку любой из трёх секций даёт курсор
`ew-resize`; тяга меняет ширину всех трёх сразу и симметрично.

Работы тут оказалось меньше, чем в постановке: все три секции уже лежат
в одном центрированном контейнере `.pipe`, поэтому «синхронно и
симметрично» — не отдельная механика, а прямое следствие. Меняется ширина
контейнера, кромки расходятся поровну сами, секции меняются заодно
независимо от того, за какую тянули.

**Коэффициент два не произволен.** Чтобы схваченная кромка не отставала
от курсора, ширина должна расти вдвое от его смещения: кромка ушла на Δ,
зеркальная на столько же, итого 2Δ. Замерено: тяга правой кромки на
+120 px дала ширину 860 → 1100, кромки сместились 320 → 200 и 1180 → 1300,
то есть ровно по 120 каждая.

Прочее:

* Пределы — от 420 px до ширины окна минус поля. При сужении окна ширина
  подрезается сама, но сохранённое значение не трогается: вернут окно —
  вернётся и ширина.
* Двойной щелчок по кромке возвращает исходные 860 px. Без этого вернуться
  к умолчанию можно было бы только на глаз.
* Стрелками влево и вправо — по 40 px, `Home` сбрасывает. Ручки получили
  `role="separator"` и попадают в обход по Tab.
* Ширина запоминается в `localStorage`, а не в хеше URL: это личная
  настройка просмотра, а хеш на этом сайте отведён под то, чем делятся
  ссылкой. Обращение к хранилищу целиком в `try` — в приватных режимах
  бросает уже само обращение, а не только запись.
* Ручки заводятся скриптом, а не лежат в разметке: это надстройка,
  без JS страница остаётся рабочей, просто нетянущейся.
* Во время тяги подсвечиваются все шесть кромок разом — так видно, что
  секции связаны, а не движется одна схваченная.

**Сделано на Pointer Events**, поэтому работает и по касанию — в отличие
от перетаскивания столбцов в обозревателе, которое сделано на HTML5
drag-and-drop и на сенсорных экранах не срабатывает вовсе (раздел 13).

### Панель байтов редактируемая

Это закрывает вторую половину исходного вопроса владельца: не только
«текст в числа», но и «числа в текст». Можно вбить `D0 96 D0 B5 D0 BD D1 8F`
и переключением кодировки чтения увидеть то `Женя`, то `Р–РµРЅСЏ`.

* Система счисления переключается DEC / HEX / BIN, уже введённые байты
  при этом не теряются — переписываются в новой системе.
* Разбор терпимый к разделителям: переживает `D0 90`, `D0,90`, `0xD0 0x90`.
  Но именно терпимый, а не молчаливый: всё неразобранное показывается
  списком. Проверка своя на каждую систему счисления — `parseInt('1F', 10)`
  вернул бы `1`, и опечатка в режиме DEC превратилась бы в тихо неверный байт.
* Правку руками страница помечает и перестаёт перезатирать байты из текста,
  пока не тронут исходный текст.

### Заголовок секции — в одной строке с её контролами

Раньше заголовок стоял отдельной строкой над панелью контролов и занимал
высоту, ничего к ней не добавляя. Теперь он первый элемент той же полосы:
слева название, дальше контролы, справа счётчик. Секции стали ниже
на 30 px каждая — при трёх секциях это почти сотня пикселей, которые
раньше уходили в пустоту.

Сделано во всех трёх секциях сразу, а не только там, где появилась кнопка:
иначе они разъехались бы по виду.

При нехватке места полоса переносится по строкам (`flex-wrap`), а не
выпихивает содержимое: на ширине конвейера 860 px всё в строку,
от 700 px и уже — переносится, но за границы секции не выходит нигде.

### Кнопка «Очистить»

Живёт в первой строке секции исходного текста, справа от заголовка. Выключается, когда поле
и так пусто — незачем предлагать действие, которое ничего не изменит.

**Очистка отменяется через Ctrl+Z.** Присваивание `value` стирает нативную
историю отмены: нажал не глядя — и текст уже не вернуть. Поэтому запись
в поле идёт через `execCommand`, и правка ложится в ту же историю, что
и набор с клавиатуры. Метод объявлен устаревшим, замены ему нет, так что
рядом лежит запасной путь на случай, если он однажды перестанет работать.

Тем же способом теперь пишет и «Прогнать обратно» — раньше оно тоже рвало
историю отмены.

Отмена возвращает не только текст: она порождает обычное событие ввода,
поэтому конвейер пересобирается сам, и байты с результатом возвращаются
вместе с ним.

На пустом поле подпись говорит «Поле пустое — впишите текст или вставьте
байты ниже», а не «0 символов, все представимы в UTF-8»: последнее
формально верно, но утверждать что-то обо всех символах, когда их нет,
незачем.

### Потери при кодировании — отдельной строкой

«Привет, мир!» в Windows-1252 теряет девять символов. Страница пишет прямо:
какие именно и сколько. Потеря — не сбой реализации, а главный сюжет:
именно из-за неё «одной кодировкой» обойтись не вышло.

### Base64 — не кодировка записи

В списки «записать как» и «прочитать как» он не попадает: он кодирует
байты, а не текст. Зато сами байты показываются в нём отдельной строкой —
это его настоящая работа, и разница видна на одном экране.

### Пробел в результате

В таблице обозревателя пробел помечается рамкой `SP` — там это правильно,
каждая строка про один байт. В результате перекодировщика текст читают
глазами, и рамка на каждом пробеле мешает: там он остаётся пробелом.
Прочие управляющие символы помечаются и здесь.

## 7. Главная страница

Задача — чтобы зашедший понял, о чём сайт, раньше, чем прочтёт первое слово.

### Преобразователь

Ящик со скруглёнными углами, внутри мигают нули и единицы разных размеров.
Слева по рельсе въезжает слово `Привет`, справа выезжает `РџСЂРёРІРµС‚` —
то же слово, записанное в UTF-8 и прочитанное как Windows-1251.

Решения, которые стоило принять осознанно:

* **Разряды раскладываются случайно, а не сеткой.** Регулярность читается
  как узор; нужен шум работающей машины. Крупные редки, мелких много —
  так ящик выглядит глубоким.
* **Разряд не сидит на месте.** Он проявляется, держится 1,2–3,6 с, гаснет
  до нуля, переезжает на новую позицию и возвращается уже другим —
  другого размера, яркости и значения. Переставляют его **только пока он
  невидим**: иначе он поехал бы по ящику на глазах, а нужно, чтобы исчез
  здесь и возник там. Поэтому переход навешен на одну прозрачность,
  координаты не анимируются вовсе.
* **У каждого разряда свой цикл со своими сроками.** Общий таймер собрал бы
  их в синхронную пульсацию — а это выглядит фоном, а не работой. Старты
  тоже разведены во времени, иначе первая волна вспыхнет разом.
* **Живой разряд иногда переключается, не сходя с места**: ящик должен
  считать, а не только мерцать.
* **Рельса проходит через всю сцену.** Без неё ящик — просто картинка,
  а не звено конвейера.
* **`prefers-reduced-motion` уважается**: движение выключается целиком,
  оба слова остаются видимыми, смысл картинки не теряется.
* Слова помечены `aria-hidden`, а рядом лежит текстовое описание для
  экранных читалок: анимация без озвучки бесполезна.

### Имена классов

Ящик называется `.blackbox`, а не `.box` — короткое имя уже занято рамками
мнемоник управляющих символов (`LF`, `NUL`) в таблицах и в легенде меню.
Совпадение было бы не косметическим: правило ящика лежит в файле позже
и перебивало бы мнемоники. Замерено — каждая рамка в таблице выросла бы
с 19×14 до 230×130 пикселей, со скруглением 16 px и тенью.

### Текст и навигация

Блок «Знакомо?» — три коротких абзаца: байты те же, правила чтения разные;
кодировка как договор, которых оказалось много; здесь механизм показан
побайтно. **Текст черновой, ждёт правки владельца.**

Дальше — карточки разделов, дублирующие боковое меню. Отсылать к бургеру
в углу нельзя: пользователь пришёл за ответом, а не за поиском меню.

### Имена файлов

Главная заняла `index.html` — на GitHub Pages это единственный правильный
адрес для точки входа. Обозреватель переехал в `explorer.html`,
скрипт `js/main.js` — в `js/explorer.js`.

## 8. Боковое меню

## 9. Отображение символов

### Шрифт: считаем, а не гадаем

Если полтаблицы — квадратики `.notdef`, студент не отличит «глифа нет
в шрифте» от «символа нет в кодировке». Вопрос решался замером.

**Что нужно покрыть.** Объединение таблиц всех кодовых страниц —
**726 символов**: латиница с диакритикой, кириллица, греческий, иврит,
арабский, рамки, заливки, валюты, математика. Набор конечен и известен
заранее.

**Чего хватает у системных шрифтов** (проверено по их cmap):

| Шрифт | Покрыто из 726 | Чего нет |
|---|---|---|
| FreeMono | 725 | только `U+F8FF` |
| DejaVu Sans | 723 | 2 арабские |
| DejaVu Sans Mono | 665 | **весь иврит (51)**, 4 арабские |
| Liberation Mono | 665 | 60 арабских |
| Noto Sans Mono | 609 | иврит и арабский |
| Fira Code | 585 | иврит, арабский, часть латиницы |

Вывод недвусмысленный: **ни один не покрывает всё**, а наш собственный
первый выбор — DejaVu Sans Mono — терял иврит целиком, то есть вся
Windows-1255 у посетителя превращалась в квадраты.

**Что положили в комплект.** Два подмножества, диапазоны не пересекаются:

| Файл | Источник | Покрывает | Размер |
|---|---|---|---|
| `CharsetsMono.woff2` | DejaVu Sans Mono | всё, кроме иврита и четырёх арабских | 20 КБ |
| `CharsetsMono-Semitic.woff2` | FreeMono | иврит, `U+0688`, `U+06BA`, `U+06C1`, `U+06D2`, `U+2044` | 2.7 КБ |

23 КБ на оба. Полные шрифты тащить незачем — нужные символы известны.

**Своя гарнитура нужна ещё и для метрик.** Ширина знака у неё ровно
0.6021 em, и на этом держится расчёт ширины столбцов. Без комплекта на
Windows подставился бы Consolas с 0.55 em, и столбцы поехали бы.

### Пять символов, которых не нарисует никакой шрифт

Из 726 в подмножества не попали ровно пять — и правильно:

* `U+200C`–`U+200F` (ZWNJ, ZWJ, LRM, RLM) — нулевой ширины по определению,
  рисовать нечего;
* `U+F8FF` — область частного использования, в MacRoman это логотип Apple.

Раньше они выводились пустой клеткой: позиция занята, а выглядит
незанятой. Лечится не шрифтом, а моделью — теперь это рамка с мнемоникой
(`ZWNJ`, `LRM`, `PUA`) и подсказкой.

### За пределами кодовых страниц

В режиме «по символу» ось идёт по всему BMP: иероглифы, деванагари,
эмодзи. Комплектом это не закрыть — одни только CJK-шрифты весят десятки
мегабайт против наших 23 КБ. Запретить браузеру подставлять системные
шрифты тоже нельзя, да и не нужно: у японца иероглифы нарисуются, у нас
нет.

Поэтому вопрос ставится иначе: **не «есть ли глиф в комплекте», а
«увидит ли его именно этот посетитель»**. Отвечает на него только тот же
движок, который и рисует, — символ выводится на канву и сравнивается
с `.notdef`.

Две грабли по дороге:

* **Сравнение по ширине не работает.** В моноширинном шрифте у `.notdef`
  ширина такая же, как у буквы: тест объявлял отсутствующей и букву «Ж».
  Сравниваем растры.
* **Пустой растр — законный вид** для пробелов, форматирующих и
  комбинирующих знаков. Первая версия пометила обычный пробел как
  отсутствующий глиф. Эти категории (`\p{White_Space}`, `\p{Cf}`,
  `\p{Cc}`, `\p{Mn}`, `\p{Me}`) проверку не проходят вовсе.

Проверка идёт лениво, `IntersectionObserver` по блокам: разом все 65 536
строк — это секунды, а блок из 32 строк — 3 мс, и результат кешируется
по кодовой точке. Найденное заменяется своим значком — рамкой с `?` —
а не оставляется браузерным квадратом: квадрат не отличить от настоящих
символов рамок, которых в CP437 половина таблицы.

Если canvas отдаёт шум (режимы приватности), проверка отключается
целиком: лучше промолчать, чем разметить таблицу наугад.

### Состояния ячейки CHAR

| Состояние | Отрисовка | Цвет |
|---|---|---|
| обычный символ | глиф | `--c-text` |
| управляющий C0/C1 | мнемоника `NUL`, `SOH`, `DEL` мелким шрифтом | `--c-control` |
| пробельные | видимый маркер (`␠`, `␉`) с подписью | `--c-control` |
| слот не назначен | `—` | `--c-unassigned` |
| суррогат / non-character | подпись типа | `--c-unassigned` |

## 10. Размер интерфейсного текста

Владелец держит правило: интерфейсный текст не мельче 14 px. В коде это
токен `--fs-ui: 14px`, и все подписи, метки, заметки, легенда и подсказки
берут размер из него — чтобы правило нельзя было незаметно нарушить
следующей правкой.

Иерархию теперь несут цвет, насыщенность, разрядка и капитель, а не кегль.
Это ограничение, но не потеря: разница между «подпись» и «текст» и так
читалась не по размеру.

### Что под правило не подпадает

* **Содержимое таблиц.** Там кегль выбирает сам пользователь регулятором
  10…24 — это его собственный инструмент, и навязывать ему пол значило бы
  спорить с его же выбором.
* **Подписи колонок `DEC/HEX/BIN` и рамки-мнемоники** привязаны к тому же
  регулятору. Жёсткий пол их сломал бы: ширина колонки считается от кегля,
  и при 14 колонка HEX выходит 37 px, а слово «HEX» четырнадцатым кеглем
  требует 45. Коэффициент подобран так, чтобы при кегле по умолчанию (22)
  подпись вышла ровно 14 px — а мельче она становится только если
  пользователь сам уменьшил таблицу.
* **Мигающие разряды в ящике на главной** — графика, а не текст; их
  разнокалиберность и есть эффект.

### Побочные следствия

* Шапка обозревателя подросла: порог, за которым она перестаёт помещаться
  в строку, сместился с ~1100 до ~1150 px. Сам недостаток был известен
  и остаётся в разделе 13.
* Пояснение к оси и шапка таблицы теперь липнут к верху одним контейнером
  `.stickytop`. Раньше у шапки стояло `top: 33px` — высота пояснения,
  вписанная числом; от укрупнения шрифта она бы поехала.

## 12. Решения владельца

1. **UTF-16** — один пункт списка с переключателем порядка байтов (LE/BE).
   BOM показываем.
2. **Верхняя граница** — до U+10FFFF. BMP остаётся лентой по умолчанию,
   плоскости 1–16 выбираются отдельно (см. раздел 4).
3. **Base64** — группа в том же списке, со своим видом таблицы.
5. **Выбор кодировки** — не комбобокс, а мультиселект с чекбоксами:
   несколько кодировок бок о бок (раздел 5).
6. **Режимы сравнения** — два, переключаются явно, без автоматики:
   «один код, разные символы» и «один символ, разные коды».
7. **Приглушение совпадающих строк** — принято, флажком, по умолчанию
   выключено.
8. **Переключение режимов** — строго вручную, никакой автоматики.
9. **Перетаскивание столбцов** — принято.
10. **Подсказки колонок** — короткие, параллельные: «…-ое представление».
4. **Тексты подсказок** — черновик в разделе 4, ждёт вычитки.

## 13. Что дальше

**Многобайтовые кодировки** — Shift_JIS, EUC-JP, EUC-KR, GBK, GB18030,
Big5. Браузер декодирует их сам, так что данные бесплатны, но модель
нужна другая:

* в режиме 1 байт получает роль (одиночный / ведущий / ведомый) — так же,
  как уже сделано для UTF-8;
* в режиме 2 нужна обратная таблица, а строится она перебором пар
  «ведущий × ведомый» — порядка 32 тысяч декодирований. Делать лениво,
  при первом обращении к кодировке, и один раз за сессию.

Это самая наглядная иллюстрация к вопросу «почему не одна кодировка»:
восточноазиатские письменности в 256 позиций не влезают физически,
и именно отсюда растут все многобайтовые схемы.

## 14. Что осталось несделанным

Список по состоянию на момент первого коммита. Проверено, а не вспомнено.

### Функциональность

* **Многобайтовые кодировки** — раздел 12. Самый крупный оставшийся кусок.
* **Плоскости выше U+FFFF** в режиме «по символу»: лента доходит до конца
  BMP, план в разделе 4.
* **Узкие экраны.** Главная и перекодировщик укладываются в 500 px,
  а у обозревателя шапка требует ~1150 px и выпихивает документ:
  контролов там семь, и в строку они не помещаются. Нужен либо перенос
  по строкам, либо часть контролов под кнопку.
* **Перетаскивание столбцов не работает на сенсорных экранах**: сделано
  на HTML5 drag-and-drop, который на них не срабатывает. Нужен вариант
  на pointer-событиях.
* **Клавиатура в списке кодировок.** В спеке заявлены стрелки и Space,
  по факту работают только Tab и Escape — то есть нативная навигация
  по чекбоксам. Формально `role="listbox"` обещает больше, чем сделано.

### Значок страницы

Выбран вариант «U+» — нотация кодовой точки: читается в 16 px и узнаётся
всяким, кто видел `U+0410`. Отвергнуты «ящик с 01» (рамка съедает место,
цифры мельчают), «А и Ð» (несёт мысль лучше всех, но в 16 px тесно)
и «байт клетками» (красиво, но не про этот сайт).

Буквы переведены в кривые. Значок грузится как отдельная картинка и до
наших `@font-face` не достаёт, так что при живом тексте его вид зависел бы
от шрифтов посетителя.

| Файл | Зачем |
|---|---|
| `favicon.svg` | основной, векторный |
| `favicon.ico` | 32 и 16 px, для браузеров без поддержки SVG-значков |
| `apple-touch-icon.png` | 180 px, закладка на домашнем экране |

Медиазапрос на светлую тему не понадобился: тёмная плитка одинаково
читается и на белой панели вкладок, и на тёмной — проверено на трёх фонах.

### Тексты, ждущие владельца

* Три абзаца на главной — черновик.
* Подсказки колонок CHAR / DEC / HEX / BIN.
* Подписи переключателя режимов «по коду / по символу».

### Проверки, которых не было

* **Только Chrome.** Firefox и Safari не проверялись вовсе, а завязок
